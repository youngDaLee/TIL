## 1.2 SQL 공유 및 재사용
### 소프트파싱 vs 하드파싱
* 라이브러리 캐시
  * 내부 프로시저를 반복 재사용 할 수 있는 공간
  * SGA의 구성 요소
* SGA
  * 서버프로세스, 백그라운드 프로세스가 공통으로 액세스하는 데이터와 제어구조를 캐싱하는 메모리공간
* 사용자 SQL 입력 -> DBMS가 SQL 파싱 -> 해당 SQL이 라이브러리 캐시에 존재하는지 확인(캐시에 존재하면 실행 / 찾지 못하면 최적화)
  * 소프트파싱 : SQL을 캐시에서 찾아 곧바로 실행단계로 넘어가는것
  * 하드파싱 : 찾는데 실패해서 최적화, 로우소스 생성 단계까지 거치는 것

=> SQL 최적화 과정이 하드한 이유
* 생각하는 것 보다 많은 일을 수행함
* 조인 순서, 조인 방식, 인덱스 스킨 방식 등을 선핵해야 하기 때문에..
* 무수히 많은 후보군 실행 결로를 도출하고 효율성을 판단

### 바인드 변수의 중요성
이름 없는 SQL 문제
* 함수, 프로시저, 트리거 등은 이름을 갖지만 SQL은 따로 이름이 없음 -> SQL 전체 텍스트가 이름 역할을 함(SQL 이름 전체로 캐싱)
* 텍스트 중 작은 부분이라도 수정되면 다른 객체가 탄생됨
* 일회성 SQL도 많기 때문에 SQL을 영구저장하지 않음(오라클, SQL Server)

공유 가능 SQL
* 의비적으로는 같지만 실행할 때 각각 최적화를 진행하고 라이브러리 별도 캐시에 저장함(파라미터만 다른경우 -> SELECT * FROM S WHERE name="a" / SELECT * FROM S WHERE name="b")
* 이렇게 되면 쿼리 날릴때마다 프로시저가 생성되어 라이브러리캐시에 쌓임
* 해결책 => 파라미터Driven 방식으로 SQL 작성 (**바인드 변수**)
