# 3.1 테이블 액세스 최소화
요약
- 인덱스 스캔이 반드시 효율적인건 아님
- 인덱스를 통해 결국 ROWID를 얻고 -> ROWID를 통해 데이터를 가져옴 -> 이 때 테이블 랜덤 액세스 발생
- 테이블 랜덤 액세스는 ROWID를 이용해 데이터 블록을 하나씩 찾아가는 과정 -> 고비용 작업
- 따라서 SQL 튜닝의 핵심은 이 액세스 횟수를 줄이는 데 있다

인덱스 스캔 vs 풀스캔
- 인덱스 + 랜덤 액세스: 한 집씩 방문해서 택배를 배달 (Single Block I/O)
- Full Table Scan: 큰 트럭에 짐을 싣고 한꺼번에 배달 (Multi Block I/O)

## 3.1.1 테이블 랜덤 액세스
인덱스로 검색하는데 느린 이유 (파티셔닝이 필요한 이유) => 대량 데이터 조회 시 인덱스가 느려짐
- 인덱스를 스캔하는 이유는 검색 조건을 만족하는 소량의 데이터를 인덱스에서 찾아 테이블레코드를 찾아가기 위한 주소값(ROWID)를 얻기 위함
- 인덱스 ROWID는 논리적 주소에 가까움
  - 물리적으로 직접 연결되지 않고 테이블 레코드를 찾아가기 위한 논리적 주소 정보를 담고있음(n번 데이터파일의 nn번 블록 nn번째 레코드) -> 포인터 같은 개념이 아님(메모리 주소를 담는 변수)
- 메인메모리 DB(MMDB)와 비교
  - MMDB : 데이터를 메모리에 로드해두고 메모리를 통해서만 IO수행하는 DB
  - 오라클처럼 디스크상 주소정보를 갖는게 아니라 메모리상 주소정보(포인터)를 가짐
- IO 매커니즘
  - DBA(=데이터파일번호+블록번호): 디스크상에서 블록을 찾기 위한 주소 정보
  - IO성능을 높이려면 버퍼캐시 활용해야함(매번 디스크 블록에서 읽을 수 없으니) -> 블록 읽을 때 읽고자하는 DBA를 기준으로 해싱된 버퍼 헤더를 찾고 버퍼헤더에서 얻은 포인터로 버퍼블록 찾아감
  - 인덱스로 테이블 블록 액세스할 때 : 리프블록에서 읽은 ROWID 분해해서 DBA정보 얻음
  - Full Scan 할 때 : 익스텐트 맵을 통해 읽을 블록들 DBA 정보 얻음
  - ROWID는 포인터가 아니기 때문에 ROWID가 가리키는 테이블블록 버퍼캐시에서 먼저 찾고 -> 없으면 디스크에서 블록 읽음
  - 모든 데이터가 버퍼캐시에 캐싱되어 있어도 테이블 레코드 찾기 위해 매번 DBA해싱-래치획득과정 반복... (동시 액세스 심할땐 체인래치, 버퍼Lock 경합까지 발생)
- 인덱스 ROWID는 고비용 연산

### 3.1.2 인덱스 클러스터링 팩터(CF)
군집성 계수. 특정 컬럼을 기준으로 같은 값을 찾는 데이터가 서로 모여있는 정도.

유사한 정보가 물리적으로 근접해있으면 효율 굳

### 3.1.3 인덱스 손익분기점
인덱스 ROWID를 이용한 테이블 액세스는 고비용 구조 -> 읽어야 할 데이터가 일정량 넘어가면 풀스캔보다 느려짐
- Index Range Scan에 의한 테이블 액세스가 Table FullScan보다 느려지는 지점을 **인덱스 손익분기점** 이라 부름
- Table Full Scan은 성능이 일정
- 인덱스를 이용한 접근은 **테이블 랜덤 액세스** 때문에 건수가 많을수록 느려짐
  - Table Full Scan은 시퀀셜 인덱스인 반면 인덱스 ROWID를 이용한 테이블 액세스는 랜덤 액세스 방식
  - Table Full Scan은 Multiblock IO인 반면 인덱스 ROWID를 이용한 테이블 액세스는 Single Block IO
- 인덱스 손익분기점은 5~20% 에서 결정됨 && CF에 따라 크게 달라짐
  - CF가 나쁘면 같은 테이블 블록 여러번 반복 액세스 해서 논리적/물리적 IO가 늘어남 -> 5%, 너무 나쁘면 1%까지 떨어지는 요인
  - CF좋으면 90% 수준까지도 올라가기도 함


온라인 프로그램 튜닝 vs 배치 프로그램 튜닝
- 온라인프로그램 : 보통 소량 데이터를 읽고 갱신해서 인덱스를 잘 활용하는게 중요. 대상 범위를 줄이는 것
- 배치프로그램 : 전체 범위 처리기준으로 튜닝. 파티션 활용 전략! 전체를 빠르게 처리하는것

### 3.1.4 인덱스 컬럼 추가
테이블 액세스를 최소화 하기 위해 일반적으로 사용하는 튜닝 기법 : 인덱스에 컬럼 추가
- 필터 조건에 의해 버려지는 레코드가 많을 때(인덱스만으로 걸러지는 데이터가 적을 때)
- 대상 범위를 줄이기 위해 복합인덱스로 튜닝

### 3.1.5 인덱스만 읽고 처리
테이블 랜덤 액세스가 많아도 필터 조건에 의해 버려지는 데이터가 거의 없다면?
- ex) `LIKE` 검색처럼 해당하는 데이터 찾고 테이블 액세스 한 후 버리는 데이터는 없지만... LIKE 조건 자체에서 액세스하는 데이터가 많을 때(쿼리에 해당하는 데이터 많을 때)
- 쩔수 없다 느린채로 사용하자
  - 반드시 개선을 해야 한담녀 쿼리에 사용된 컬럼을 모두 인덱스에 추가해서 테이블 액세스 아예 발생 안하도록 covered 쿼리로 만든느 것


include 인덱스
- 오라클에는 없지만 SQL Server 2005버전에 추가된 기능
- 인덱스 키 외에 미리 지정한 컬럼을 리프레벨에 함께 저장
  - 인덱싱 안해도 covered 쿼리로 가능 -> 테이블 랜덤 액세스 줄이는 용도

### 3.1.6 인덱스 구조 테이블
인덱스를 이용한 테이블 액세스가 고비용구조이니 랜덤 액세스가 발생하지 않도록 테이블을 인덱스 구조로 생성하는 방식 => IOT (MS SQL에서는 클러스터형 인덱스)
- 테이블을 찾아가기 위한 ROWID를 갖는 일반 인덱스와 달리 IOT는 그 자리에 테이블 데이터를 가짐
  - 테이블 블록에 있어야 할 데이터를 인덱스 리프 블록에 저장
  - IOT에서는 인덱스 리프블록이 데이터 블록
- (일반 테이블은 `힙 구조 테이블` 이라고 부름)
- IOT는 인위적으로 CF를 좋게 만드는 방법 중 하나.
- 같은 값을 가진 레코드들이 100% 정렬된 상태로 모여있어 랜덤 액세스가 아닌 시퀀셜 방식으로 액세스

### 3.1.7 클러스터 테이블
인덱스 클러스터 테이블
- 클러스터 키 값이 같은 레코드를 한 블록에 모어서 저장하는 구조
- 한 블록에 모두 담을 수 없을땐 새로운 블록을 할당해 클러스터 체인으로 연결
- 다중 테이블 클러스터 : 여러 테이블 레코드를 같은 블록에 저장
- 클러스터 인덱스도 B Tree 인덱스 구조 사용하지만 테이블 레코드 일일이 가리키지 않고 키 값을 저장하는 첫번째 데이터 블록 가리킴
  - 일반 테이블 : 1:1대응관계
  - 클러스터 인덱스 : 1:M 관계 -> 클러스터 인덱스 키값은 유니크하다
- 클러스터 인덱스 스캔할때는 랜덤 액세스가 값 하나당 한번


해시 클러스터 테이블
- 인덱스를 사용하지 않고 해시 알고리즘을 사용해서 찾아가는 인덱스 클러스터 테이블
