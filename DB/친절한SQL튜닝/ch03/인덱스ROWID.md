## 1. 인덱스에 포인터 대신 ROWID를 저장하는 이유

포인터를 쓰지 않는 이유 : **데이터의 가변성**

* **데이터의 이동**
  * 테이블의 데이터는 업데이트로 인해 위치가 변하거나(Row Chaining/Migration), DB가 재시작되면서 메모리 주소가 바뀔 수 있음
  * 만약 직접적인 메모리 포인터를 저장했다면 데이터가 움직일 때마다 수백만 개의 인덱스 레코드를 일일이 수정해야 함
* **간접 참조의 유연성**
  * ROWID는 `DBA(데이터파일 번호 + 블록 번호 + 로우 번호)`라는 **논리적 주소** 정보를 담고 있음
  * 이 정보를 가지고 **'버퍼 캐시'라는 중간 지점**을 거쳐서 데이터를 찾음

> **핵심 원리:**
> 인덱스는 테이블 레코드를 가리키는 **식별자(ROWID)**를 가질 뿐이며, 실제 위치를 찾아가는 과정은 매번 '주소록(버퍼 캐시)'을 뒤져서 확인하는 절차를 거칩니다. 
> 이 과정에서 발생하는 비용이 바로 '테이블 랜덤 액세스 비용'입니다.

## 2. 클러스터링 팩터(Clustering Factor, CF)

클러스터링 팩터는 **"인덱스 정렬 순서와 테이블 데이터의 물리적 정렬 순서가 얼마나 일치하는가"**를 나타내는 수치

### 조절 가능한 영역인가?

**가능은 하지만 매우 비싼 작업**
클러스터링 팩터를 인위적으로 개선하려면 **테이블을 인덱스 순서에 맞춰 새로 재생성(Reorg)**해야함

* 특정 인덱스(A)를 기준으로 테이블을 재정렬하면 A 인덱스의 CF는 좋아지지만, 다른 인덱스(B)의 CF는 나빠질 수 있습니다.
* 따라서 가장 자주 쓰이는 핵심 인덱스를 기준으로 테이블 데이터를 물리적으로 재배치하는 결단이 필요합니다.

### 어떻게 판단하는가?

데이터 사전(`USER_INDEXES`)의 `CLUSTERING_FACTOR` 수치를 보고 판단

* **Good CF:** 수치가 테이블의 **총 블록(Blocks) 수**에 가깝습니다. (인덱스를 따라갈 때 같은 블록을 계속 만나서 I/O가 적음)
* **Bad CF:** 수치가 테이블의 **총 로우(Rows) 수**에 가깝습니다. (인덱스 레코드를 하나 넘길 때마다 다른 블록으로 튀어야 해서 I/O가 극대화됨)
